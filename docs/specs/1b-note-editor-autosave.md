# to-spec 1b: Note พื้นฐาน, Editor, Autosave และตรวจบันทึกชนกัน

สถานะ: **ร่างรอผู้ใช้ตรวจ** (ปรับ 2026-10-21 หลังผู้ใช้ตัดสินใจ 9 เรื่อง) ยังไม่เขียนโค้ด ยังไม่ commit ทำต่อจาก [1a](1a-foundation-and-account.md) (ใช้ตัวช่วย "ผู้ใช้ปัจจุบัน", PostgreSQL + EF Core, รูปแบบ error `problem+json`, ธีมมืด, ชุดเทสต์ต่อฐานข้อมูลจริง)

ป้ายกำกับ: **[ตัดสินแล้ว]** ผู้ใช้ยืนยัน (อ้างแหล่ง) · **[ร่าง]** ผู้ช่วยเสนอ รอผู้ใช้ตรวจ · **[ยังไม่ได้ตรวจ]** ยังไม่มีหลักฐานทดสอบ

## Problem Statement

ตอนนี้ผู้ใช้เข้าระบบได้แล้ว (1a) แต่ยังจดอะไรไม่ได้เลย Jod คือแอป "จดก่อน จัดทีหลัง" ผู้ใช้ต้องการเปิดแล้วเขียนได้ทันที เนื้อหาเป็น Block ที่ซ้อนกันได้ (รายการ, Checklist, Toggle) ใช้เมนู `/` สร้าง Block ได้ทั้งบนคอมพิวเตอร์และบนมือถือ และต้องไม่เสียเนื้อหาที่พิมพ์ไป ไม่ว่าจะลืมกดบันทึก เน็ตหลุดชั่วคราว หรือเปิด Note เดียวกันไว้สองแท็บ

## Solution

ผู้ใช้กด "New note" แล้วเขียนได้ทันที (Title เริ่มต้น "Untitled") มี Title, ช่อง Context และเนื้อหาแบบ Block ที่เปิดเมนู `/` สร้าง Block ได้ ระบบบันทึกเองเมื่อหยุดพิมพ์ประมาณ 1 วินาทีและเมื่อออกจากหน้า พร้อมแสดงสถานะ "กำลังบันทึก / บันทึกแล้ว / บันทึกไม่สำเร็จ" ถ้าบันทึกไม่สำเร็จเนื้อหายังอยู่ในจอและกดลองใหม่ได้ ถ้าเปิด Note เดียวกันสองแท็บแล้วบันทึกชนกัน ระบบหยุดและให้เลือก ใช้ฉบับนี้ / ใช้ฉบับอีกแท็บ / เก็บทั้งสอง โดยมองเห็นสองฉบับเทียบกัน (Side-by-side บนจอกว้าง สลับดูทีละฝั่งบนมือถือ) มีรายการ Note ของตัวเองให้เปิดกลับมาแก้ ใช้ได้บนมือถือและคอมพิวเตอร์ ธีมมืด

## User Stories

1. ในฐานะผู้ใช้ ฉันต้องการกด New note แล้วเขียนได้ทันทีโดยไม่ต้องตั้งชื่อ เพื่อจดความคิดได้ทันก่อนลืม
2. ในฐานะผู้ใช้ ฉันต้องการให้เคอร์เซอร์อยู่ในเนื้อหาเมื่อสร้าง Note ใหม่ เพื่อพิมพ์ได้เลยไม่ต้องคลิกก่อน
3. ในฐานะผู้ใช้ ฉันต้องการให้ Title เริ่มต้นเป็น "Untitled" และแก้ชื่อได้ในที่เดิม เพื่อตั้งชื่อทีหลังเมื่อพร้อม
4. ในฐานะผู้ใช้ ฉันต้องการให้ Title ที่ลบจนว่างกลับเป็น "Untitled" เพื่อไม่มี Note ที่ไม่มีชื่อแสดงในรายการ
5. ในฐานะผู้ใช้ ฉันต้องการช่อง Context แยกจากเนื้อหา เพื่อเขียนจุดประสงค์ของ Note ไว้ให้ AI ใช้ในอนาคต
6. ในฐานะผู้ใช้ ฉันต้องการเห็นรายการ Note ของฉันเรียงจากที่แก้ล่าสุด เพื่อเปิด Note ที่เพิ่งทำกลับมาได้เร็ว
7. ในฐานะผู้ใช้ ฉันต้องการเปิด Note จากรายการแล้วเห็นเนื้อหาครบ เพื่อแก้ต่อได้
8. ในฐานะผู้ใช้ ฉันต้องการเปิดเมนู `/` ด้วยการพิมพ์ `/` เพื่อสร้าง Block โดยไม่ต้องยกมือจากแป้นพิมพ์
9. ในฐานะผู้ใช้ ฉันต้องการสร้าง Paragraph, Heading 1–3, Bullet list, Numbered list, Checklist, Toggle, Quote, Code และเส้นแบ่งจากเมนู `/` เพื่อจัดโครงสร้างโน้ตได้
10. ในฐานะผู้ใช้ ฉันต้องการพิมพ์ต่อหลัง `/` เพื่อกรองคำสั่ง และให้ชื่อคำสั่งที่ตรงทุกตัวอักษรขึ้นมาก่อน เช่น `/h1` ได้ Heading 1
11. ในฐานะผู้ใช้ ฉันต้องการกด Escape ปิดเมนู `/` แล้วข้อความเดิมไม่หายและเขียนต่อจากตำแหน่งเดิมได้ เพื่อไม่เสียงานเมื่อเปิดเมนูโดยไม่ตั้งใจ
12. ในฐานะผู้ใช้ ฉันต้องการเลือกคำสั่งด้วยการแตะหรือคลิกแล้วพิมพ์ต่อทันทีโดยตัวอักษรไม่หาย ไม่ไปผิดที่ เพื่อพิมพ์ต่อเนื่องบนมือถือได้
13. ในฐานะผู้ใช้มือถือ ฉันต้องการให้เมนู `/` ไม่ถูกแป้นพิมพ์บัง และเลื่อนดูรายการที่เหลือได้ เพื่อเลือกคำสั่งได้จริง
14. ในฐานะผู้ใช้ ฉันต้องการซ้อน Bullet, Numbered, Checklist และ Toggle ได้หลายชั้นโดยใส่ Block ชนิดไหนไว้ข้างในก็ได้ เพื่อจัดโครงสร้างตามความคิด
15. ในฐานะผู้ใช้ ฉันต้องการเยื้อง/ถอยระดับของรายการด้วยแป้นพิมพ์ (Tab / Shift+Tab) และบนมือถือด้วยปุ่มบนจอ เพื่อซ้อนรายการได้โดยไม่ต้องลาก
16. ในฐานะผู้ใช้ ฉันต้องการพับและขยาย Toggle เพื่อซ่อนรายละเอียดที่ไม่ต้องการเห็นตอนนี้
17. ในฐานะผู้ใช้ ฉันต้องการติ๊ก Checklist ได้ และให้สถานะที่ติ๊กถูกบันทึกด้วย
18. ในฐานะผู้ใช้ ฉันต้องการให้ระบบบันทึกเองเมื่อฉันหยุดพิมพ์ประมาณ 1 วินาที เพื่อไม่ต้องกดบันทึกเอง
19. ในฐานะผู้ใช้ ฉันต้องการให้ระบบบันทึกเมื่อฉันออกจากหน้าหรือสลับ Note หรือสลับแอปบนมือถือ เพื่อไม่เสียสิ่งที่พิมพ์ล่าสุด (บนมือถือ ถ้าโน้ตใหญ่เกินที่ส่งตอนซ่อนแท็บได้ ระบบแสดง "ยังไม่บันทึก" และอาจเสียส่วนล่าสุด เป็นข้อจำกัดที่รู้กัน)
20. ในฐานะผู้ใช้ ฉันต้องการให้ระบบบันทึกอย่างน้อยทุก 10 วินาทีขณะที่ฉันพิมพ์ต่อเนื่อง เพื่อไม่เสียงานยาวๆ ถ้าเครื่องค้าง
21. ในฐานะผู้ใช้ ฉันต้องการเห็นสถานะ "กำลังบันทึก / บันทึกแล้ว / บันทึกไม่สำเร็จ" เพื่อรู้ว่างานปลอดภัยหรือยัง
22. ในฐานะผู้ใช้ ฉันต้องการให้คำว่า "บันทึกแล้ว" ขึ้นก็ต่อเมื่อเซิร์ฟเวอร์รับเนื้อหาล่าสุดแล้วจริง (ไม่ใช่เนื้อหาที่พิมพ์เพิ่มระหว่างรอ) เพื่อไม่ถูกหลอก
23. ในฐานะผู้ใช้ ฉันต้องการให้เมื่อเน็ตหลุดหรือเซิร์ฟเวอร์ล้มชั่วคราว ระบบลองใหม่เอง 3 ครั้งก่อนบอกว่าล้มเหลว เพื่อไม่ต้องกังวลกับปัญหาสั้นๆ
24. ในฐานะผู้ใช้ ฉันต้องการเห็น "บันทึกไม่สำเร็จ" พร้อมปุ่มลองใหม่และเนื้อหายังอยู่ในจอครบ ถ้าเป็นสาเหตุที่ลองใหม่ไม่ช่วย (เช่น โน้ตใหญ่เกิน) ให้เห็นสาเหตุเป็นภาษาไทยและมีปุ่มคัดลอกเนื้อหา เพื่อกลับมากดบันทึกใหม่ได้เมื่อเน็ตกลับมา หรือเก็บงานไว้ก่อนออก
25. ในฐานะผู้ใช้ ฉันต้องการให้ระบบเตือนก่อนปิดแท็บเมื่อมีสิ่งที่ยังไม่ได้บันทึก เพื่อไม่ปิดทิ้งโดยไม่ตั้งใจ
26. ในฐานะผู้ใช้ ฉันต้องการให้การเข้าระบบที่หมดอายุกลางการพิมพ์ถูกต่ออายุเงียบๆ แล้วบันทึกต่อ เพื่อไม่ถูกขัดจังหวะ (ใช้กลไกของ 1a)
27. ในฐานะผู้ใช้ ฉันต้องการให้ระบบรู้เมื่อ Note เดียวกันถูกแก้ไปแล้วจากอีกแท็บ และไม่เขียนทับเงียบๆ เพื่อไม่เสียงานของแท็บใดแท็บหนึ่ง
28. ในฐานะผู้ใช้ ฉันต้องการหน้าบันทึกชนกันที่แสดงฉบับในแท็บนี้เทียบกับฉบับอีกแท็บ เพื่อตัดสินใจได้ว่าจะเก็บอะไร
29. ในฐานะผู้ใช้ ฉันต้องการเลือก "ใช้ฉบับนี้" เพื่อให้เนื้อหาในแท็บนี้ทับฉบับอีกแท็บ
30. ในฐานะผู้ใช้ ฉันต้องการเลือก "ใช้ฉบับอีกแท็บ" เพื่อทิ้งสิ่งที่แก้ในแท็บนี้และโหลดฉบับล่าสุดมาแทน
31. ในฐานะผู้ใช้ ฉันต้องการเลือก "เก็บทั้งสอง" เพื่อเก็บฉบับในแท็บนี้เป็น Note ใหม่ (ชื่อต่อท้าย "(สำเนา)") และ Note เดิมคงฉบับที่อยู่ในระบบ ไม่มีฉบับไหนหายเงียบๆ
32. ในฐานะผู้ใช้มือถือ ฉันต้องการหน้าบันทึกชนกันที่สลับดูทีละฝั่งได้ เพราะจอแคบเกินกว่าจะเทียบสองฝั่ง
33. ในฐานะผู้ใช้ ฉันต้องการให้การลองส่งซ้ำหลังเน็ตสะดุด (ที่จริงเซิร์ฟเวอร์รับไปแล้ว) ไม่ถูกมองเป็นบันทึกชนกัน เพื่อไม่ต้องเจอหน้าชนกันโดยไม่มีเหตุ
34. ในฐานะผู้ใช้ ฉันต้องการเห็นเฉพาะ Note ของฉันเอง และเปิด Note ของคนอื่นไม่ได้แม้รู้รหัส เพื่อความเป็นส่วนตัว
35. ในฐานะผู้ใช้มือถือ ฉันต้องการรายการ Note ที่เปิดเป็นลิ้นชักและปิดได้ เพื่อให้พื้นที่เขียนเต็มจอ
36. ในฐานะผู้ใช้คอมพิวเตอร์ ฉันต้องการแถบข้างที่ซ่อนและแสดงได้ เพื่อให้พื้นที่เขียนโล่งตามทิศทาง UX ที่เลือกไว้
37. ในฐานะผู้ใช้ ฉันต้องการพิมพ์ภาษาไทยด้วยแป้นพิมพ์มือถือจริงได้โดยตัวอักษรไม่หายไม่ซ้ำ (IME) เพราะโน้ตของฉันเป็นภาษาไทย
38. ในฐานะผู้ใช้ ฉันต้องการธีมมืดที่คอนทราสต์ผ่าน WCAG AA และใช้แป้นพิมพ์ควบคุมได้ เพื่อใช้งานได้สบายและทุกคนเข้าถึงได้
39. ในฐานะผู้ใช้ ฉันต้องการเห็นข้อความภาษาไทยพร้อมรหัสอ้างอิงเมื่อเกิดข้อผิดพลาดของระบบ เพื่อแจ้งผู้ดูแลได้ (ใช้กลไกของ 1a)
40. ในฐานะผู้ดูแลระบบ ฉันต้องการให้เนื้อหา Note ไม่ปรากฏใน log และ error เพื่อไม่เก็บข้อมูลส่วนบุคคล
41. ในฐานะผู้ดูแลระบบ ฉันต้องการให้เซิร์ฟเวอร์ตรวจโครงสร้างและขนาดเนื้อหาก่อนเก็บ เพื่อไม่ให้ข้อมูลเสียหรือใหญ่เกินเข้าฐานข้อมูล
42. ในฐานะนักพัฒนา ฉันต้องการให้ทุก Block มีรหัสประจำตัวคงที่ตลอดการบันทึกซ้ำ เพื่อให้ฟีเจอร์ AI รอบถัดไปเทียบทีละ Block ได้ (ADR 0005)
43. ในฐานะผู้ใช้ ฉันต้องการให้ระบบถามก่อนสลับ Note ถ้า Note ปัจจุบันยังบันทึกไม่เสร็จหรือบันทึกไม่สำเร็จ เพื่อไม่เสียสิ่งที่พิมพ์โดยไม่รู้ตัว
44. ในฐานะผู้ใช้ ฉันต้องการให้แท็บที่ยังไม่ได้แก้อะไร ดึงฉบับล่าสุดเมื่อฉันกลับมาที่แท็บ เพื่อไม่เจอหน้าชนกันโดยไม่จำเป็น
45. ในฐานะผู้ใช้ ฉันต้องการให้หน้าชนกันแก้เนื้อหาไม่ได้ระหว่างตัดสินใจ ถามยืนยันก่อนทิ้งฉบับใดฉบับหนึ่ง และมีปุ่มคัดลอกฉบับที่จะทิ้ง เพื่อไม่เสียงานโดยพลาดมือ

## Implementation Decisions

**ตัดสินแล้ว (จากเอกสารเดิมและคำตอบของผู้ใช้ 2026-10-20)**

- **[ตัดสินแล้ว]** เนื้อหาทั้ง Note เก็บเป็นเอกสาร JSON ก้อนเดียว (`jsonb`) โครงสร้างเป็นของ Jod ไม่ผูกกับ TipTap ทุก Block มีรหัสคงที่ (ADR 0005) Editor ใช้ TipTap (ADR 0003)
- **[ตัดสินแล้ว]** ตรวจบันทึกชนกันด้วยเลขเวอร์ชันต่อ Note เพิ่มทีละ 1 ทุกครั้งที่บันทึก (ครอบคลุม Title เนื้อหา Context) ไม่มีช่องทางข่าวสดข้ามแท็บ (ADR 0005)

**ร่าง (ผู้ช่วยเสนอ รอผู้ใช้ตรวจ)**

- **ข้อมูล Note:** ตารางเดียวเก็บ รหัส (Guid), เจ้าของ (`OwnerId` ตามที่ 1a ระบุไว้), Title, Context, เนื้อหา (`jsonb`), เลขเวอร์ชัน (เริ่ม 1), วันที่สร้าง/แก้ (UTC) ไม่มีคอลัมน์ Parent, สถานะลบ, ข้อความล้วนสำหรับค้นหา (ทั้งหมดเป็นของงานถัดไปและเพิ่มภายหลังได้ด้วย migration) การสร้างตารางนี้ทำได้เพราะ to-spec นี้เป็นคำขอที่ชัดเจนตามกฎ `backend/CLAUDE.md`
- **ชุดค่าจำกัด:** Title ไม่เกิน 200 ตัวอักษร, Context ไม่เกิน 2,000 ตัวอักษร, เนื้อหาไม่เกิน 1 MB เมื่อเป็น JSON, ความลึกการซ้อนไม่เกิน 100 ชั้น (กฎผลิตภัณฑ์คือไม่จำกัด เพดานนี้กันเซิร์ฟเวอร์ล้มจาก JSON ลึกผิดปกติ) ค่าเหล่านี้เป็นค่าตั้งค่า ปรับได้ **[ร่าง]** 1 MB นับเป็นไบต์ UTF-8 ของ JSON เนื้อหา, 200/2,000 นับเป็นตัวอักษร Unicode (code point) เพดานความลึก 100 ชั้นเป็นความลึกของ Block ไม่ใช่ความลึก JSON ต้องตั้งขีด JSON ฝั่งเซิร์ฟเวอร์ให้พอ (ค่าเริ่มต้น 64 ชั้นรับ Block ได้แค่ราว 30 ชั้น)
- **Title ว่าง:** ถ้าบันทึกด้วย Title ที่ว่างหรือมีแต่ช่องว่าง เซิร์ฟเวอร์เก็บเป็น "Untitled" ใช้ฟังก์ชันปรับค่าเดียวกันทั้งสองฝั่ง (ตัดช่องว่างหัวท้าย, ว่าง = "Untitled") และมีเทสต์กำกับกฎนี้
- **โครงเอกสารเนื้อหา:** `{ schemaVersion: 1, blocks: [...] }` แต่ละ Block มี `id` (Guid, ผู้สร้างฝั่งหน้าเว็บเป็นคนตั้งและต้องคงเดิมทุกครั้งที่บันทึก), `type`, ข้อความของ Block, คุณสมบัติเฉพาะชนิด (Heading มี `level` 1–3, Checklist มี `checked`, Code มี `language` ไม่บังคับ) และ `children` Block ที่มี `children` ได้ มีแค่ Bullet, Numbered, Checklist, Toggle (1 Block ต่อ 1 รายการ ลูกซ้อนใน `children`) ส่วน Paragraph, Heading, Quote, Code, Divider ไม่มีลูก สถานะพับ/ขยายของ Toggle เป็นของหน้าจอ ไม่เก็บ
- **ข้อความใน Block:** 1b เก็บเป็นข้อความล้วน ไม่มีตัวหนา/เอียง/โค้ดในบรรทัด เพราะ product-spec ไม่ได้ระบุการจัดรูปแบบในบรรทัด (ดู Further Notes) ปิดส่วนขยายของ TipTap ที่ให้ผลนั้น เพื่อไม่ให้ผู้ใช้สร้างสิ่งที่บันทึกไม่ได้ ปิดส่วนขยาย Link ของ starter-kit ด้วย (ADR 0003 ระบุว่า starter-kit รวมลิงก์) การวางเนื้อหาจากภายนอกเป็นข้อความล้วน แยกบรรทัดเป็น Paragraph
- **ตรวจเนื้อหาฝั่งเซิร์ฟเวอร์:** รับเฉพาะชนิดที่อนุญาต, `id` เป็น Guid และไม่ซ้ำกันในเอกสาร, ลูกเฉพาะชนิดที่มีลูกได้, `level` อยู่ใน 1–3, ขนาดและความลึกไม่เกินเพดาน ผิดกติกา = 400 พร้อมข้อความไทยและ `reference` ไม่เปิดเผยโครงสร้างภายใน `baseVersion` ที่ขาดหรือไม่ใช่เลข = 400 เช่นกัน
- **API (ใต้ `/api` ต้องล็อกอินทุกตัว):**
  - สร้าง Note: รับ Title/Context/เนื้อหาได้ (ไม่ส่งก็ได้ ค่าเริ่มต้น "Untitled", ว่าง, ว่าง) ตอบ 201 พร้อม Note ทั้งชุดและเลขเวอร์ชัน 1
  - รายการ Note ของผู้ใช้: ส่งเฉพาะรหัส, Title, เวลาแก้ล่าสุด เรียงแก้ล่าสุดก่อน ไม่ส่งเนื้อหา ไม่แบ่งหน้าใน 1b (เป้าไม่เกินหลักหมื่น Note ต่อบัญชี ทบทวนเมื่อมี Tree)
  - อ่าน Note เดียว: ตอบ Note ทั้งชุด
  - บันทึก Note: รับ Title, Context, เนื้อหา และ `baseVersion` (เลขที่ผู้เรียกเห็นล่าสุด) ถ้าเลขตรงกับของเซิร์ฟเวอร์ → เก็บ เพิ่มเลข 1 ตอบ 200 พร้อม Note ใหม่ ถ้าไม่ตรง → 409 `problem+json` แนบ Note ปัจจุบันบนเซิร์ฟเวอร์มาด้วย (ให้หน้าชนกันเทียบได้โดยไม่ต้องขอเพิ่ม) ข้อมูลที่แนบอ่านจากฐานข้อมูล ไม่ใช่เนื้อหาของคำขอ และห้ามเขียนลง log (ต้องขยายตัวสร้าง error ของ 1a ตามข้อตัดสินใจงานแก้ 1a) การเช็กเลขและเขียนต้องเป็นขั้นตอนเดียวในฐานข้อมูล (อัปเดตแบบมีเงื่อนไขเลขเวอร์ชัน ดูแถวที่กระทบ) เพื่อให้สองคำขอพร้อมกัน หนึ่งสำเร็จ อีกหนึ่ง 409
  - Note ที่ไม่มีหรือเป็นของคนอื่น: ตอบ 404 เหมือนกัน ไม่บอกว่ามีอยู่
  - ลักษณะ JSON camelCase ตามที่ 1a กำหนด
- **ส่งซ้ำหลังเน็ตสะดุด:** กรณีเซิร์ฟเวอร์เก็บสำเร็จแต่ตอบไม่ถึง คำขอลองใหม่จะมีเลขเก่าและได้ 409 ฝั่งหน้าเว็บเทียบ Note ปัจจุบันใน 409 กับสิ่งที่ส่งไปจริง (snapshot ตอนส่ง ไม่ใช่ข้อความล่าสุดในจอ) ได้แก่ Title, Context, เนื้อหา หลังปรับ Title ด้วยกฎร่วมและเทียบแบบโครงสร้าง ถ้าเท่ากัน ถือว่าบันทึกสำเร็จและรับเลขเวอร์ชันใหม่ ไม่เปิดหน้าชนกัน
- **ทางเลือกในหน้าชนกัน (ไม่เพิ่ม endpoint):** "ใช้ฉบับนี้" = บันทึกใหม่ด้วย `baseVersion` เป็นเลขของ Note ปัจจุบันที่ได้มากับ 409 (ถ้าชนอีกให้กลับหน้าชนกันด้วยฉบับล่าสุด ลองได้ไม่เกิน 3 ครั้งแล้วแจ้งผู้ใช้) ต้องถามยืนยันก่อนทิ้งงานของอีกแท็บ และมีปุ่มคัดลอกฉบับอีกแท็บ · "ใช้ฉบับอีกแท็บ" = ทิ้งสิ่งที่แก้ในแท็บนี้ แล้วใช้ Note ปัจจุบันที่ได้มากับ 409 ต้องถามยืนยัน และมีปุ่มคัดลอกฉบับในแท็บนี้ก่อนทิ้ง · "เก็บทั้งสอง" = สร้าง Note ใหม่จากฉบับในแท็บนี้ (ทุก Block ได้เลขประจำตัวใหม่ ชื่อต่อท้าย "(สำเนา)") แล้วใช้ Note ปัจจุบันเป็นฉบับของหน้านี้ ถ้าสร้าง Note ใหม่ไม่สำเร็จ ยังอยู่ที่หน้าชนกันโดยฉบับในแท็บยังครบ ระหว่างอยู่ในหน้าชนกัน Editor เป็นอ่านอย่างเดียว และ "ฉบับในแท็บนี้" คือข้อความล่าสุดในจอ
- **เครื่องจักรสถานะ Autosave ฝั่งหน้าเว็บ:** ตรรกะล้วน (ไม่ผูก React/TipTap/เวลาจริง) รับเหตุการณ์ แก้เนื้อหา, ถึงเวลาหน่วง, ถึงเพดานรอ, บันทึกสำเร็จ/ล้มเหลวชั่วคราว/ล้มเหลวถาวร, 409, ออกจากหน้า, ส่งทิ้งท้ายแล้วยังไม่ทราบผล, กลับมาที่แท็บ, ผู้ใช้สลับ Note, ลองใหม่ด้วยมือ ส่งออกสถานะ (ไม่มีอะไรค้าง / มีสิ่งที่ยังไม่บันทึก / กำลังบันทึก / รอลองใหม่ / บันทึกแล้ว / ล้มเหลวถาวร (พร้อมสาเหตุ) / ชนกัน) และคำสั่งให้ทำ (ส่งคำขอ, ตั้งเวลา) ทำให้ทดสอบด้วย Vitest ได้ โดยใช้นาฬิกาจำลอง การแก้เนื้อหาระหว่างที่กำลังบันทึก ทำให้ฉบับที่บันทึกเสร็จไม่ใช่ฉบับล่าสุด จึงต้องบันทึกอีกรอบและยังไม่แสดง "บันทึกแล้ว" **[ร่าง]** กฎเพิ่ม: ลองใหม่ส่งฉบับล่าสุดเสมอ, timeout ของคำขอ 15 วินาที, 408/429 นับเป็นความผิดพลาดชั่วคราว, การต่ออายุโทเคนทำที่ `core/http` ทางเดียว (ตัวเครื่องจักรเห็นแต่ผลสุดท้าย) และต่ออายุล่วงหน้าเมื่อมีข้อความยังไม่บันทึกและโทเคนใกล้หมด
- **การบันทึกตอนซ่อนแท็บ:** ใช้ `fetch` แบบ `keepalive` พร้อม Authorization ตามที่ตัดสินไว้ หลังส่งถือว่า "ยังไม่ทราบผล" ต้องดึง Note ล่าสุดก่อนบันทึกครั้งต่อไป ถ้าเกินขนาดที่ `keepalive` ส่งได้ แสดง "ยังไม่บันทึก" และเตือนบนคอมพิวเตอร์ (ดูข้อตัดสินใจ D2 ด้านบน) **[ร่าง]** ใช้ `pagehide` ร่วมกับ `visibilitychange` (เป็น hidden) เพราะ `beforeunload` ไม่ยิงบนมือถือบางรุ่น **[ยังไม่ได้ตรวจ]** ขนาดจำกัดจริงของ body คำขอ `keepalive` (ราว 64 KiB) ในเบราว์เซอร์ที่รองรับ ตรวจก่อนลงมือ
- **Editor (TipTap):** ใช้แพ็กเกจในรายการ ADR 0003 เท่าที่ชนิด Block ของ 1b ต้องใช้ (starter-kit, task-list, details) และ suggestion สำหรับเมนู `/` Block ใหม่ที่ Editor สร้างต้องได้ `id` คงที่ ทุกครั้งที่ Note ถูกโหลดและบันทึกใหม่ `id` เดิมต้องไม่เปลี่ยน **[ยังไม่ได้ตรวจ]** ว่าแพ็กเกจ TipTap ที่ให้รหัสประจำ Block เป็น MIT และใช้ได้ฟรีหรือไม่ (ADR 0003 ตรวจเฉพาะ 5 แพ็กเกจ) ถ้าไม่ได้ ให้เขียนเอง ตรวจก่อนลงมือ
- **การแปลงเอกสาร:** ตัวแปลงตรรกะล้วนระหว่างเอกสาร Block ของ Jod กับโครงของ TipTap อยู่ใน `utils/` ของโมดูล `modules/notes/` ทดสอบได้ด้วย Vitest (ไปกลับแล้วเท่าเดิม รวมกรณีซ้อนลึกและ `id` คงเดิม)
- **เมนู `/` ใน 1b:** `/text`, `/h1`–`/h3`, `/bullet`, `/numbered`, `/todo`, `/quote`, `/divider`, `/code`, `/toggle` ตามผล prototype 022 ที่ต้องคงไว้: ชื่อคำสั่งที่ตรงทุกตัวอักษรอยู่อันดับแรก, คืนตำแหน่งเคอร์เซอร์ในจังหวะเดียวกับที่ข้อความเปลี่ยน (ไม่รอเฟรมถัดไป), เมนูเลือกด้านบนหรือล่างของบรรทัดตามที่ว่างที่เหลือรวมแป้นพิมพ์มือถือและจำกัดความสูงให้เลื่อนได้ คำสั่ง `/note`, `/reference`, `/link`, `/image`, `/file`, `/callout` ยังไม่อยู่ในเมนูจนกว่า Block นั้นจะมี
- **Layout และหน้าจอ:** workspace แถบข้างซ้าย (ปุ่ม New note + รายการ Note) และ canvas เขียนโล่ง Title ใหญ่ ไม่มีกรอบ การ์ด เส้นแบ่ง หรือแถบล่าง ตามทิศทางที่เลือกใน ticket 017 แถบข้างซ่อน/แสดงได้บนจอกว้าง (~300px แถบข้าง เนื้อหา max ~600px ชิดซ้าย) บนมือถือแถบข้างเป็นลิ้นชัก ตำแหน่งช่อง Context และตัวบอกสถานะการบันทึกในหน้า ให้เสนอรูปเมื่อลงมือและขอผู้ใช้ยืนยัน หน้าชนกัน: จอกว้างเทียบสองฝั่ง (ซ้าย "ฉบับในแท็บนี้", ขวา "ฉบับอีกแท็บ") จอแคบสลับดูทีละฝั่งด้วยแท็บสองปุ่ม มีปุ่ม 3 ทางเลือกอยู่ที่เดียวกันทั้งสองแบบ **[ร่าง]** จุดตัดจอแคบเดียว (เสนอ 768px) ลิ้นชักบนมือถือต้องมี focus trap Tab ใน Editor ออกได้ด้วย Esc ปุ่ม New note สร้าง Note บนเซิร์ฟเวอร์ก่อนเปิด ปิดปุ่มระหว่างสร้าง แสดงข้อผิดพลาดถ้าล้ม
- **ชุดสี/ธีม:** ขยายตัวแปร CSS ของ 1a ให้ครอบคลุมทั้งแอป (พื้นหลัง, แถบข้าง, ตัวอักษร, สีเน้น, สถานะบันทึก/ผิดพลาด/ชนกัน, เมนู) คอนทราสต์ WCAG AA ทุก state ของ interactive element
- **ชื่อ/ชนิดใหม่ที่เสนอ (ตามกฎ `backend/CLAUDE.md` ต้องขอผู้ใช้ยืนยันก่อนตั้ง):** `Note` (entity), `INoteService`, `NoteService`, `CreateNoteRequestModel`, `UpdateNoteRequestModel`, `NoteViewModel`, `NoteListItemViewModel`, `NotesController` ฝั่งหน้าเว็บโมดูล `modules/notes/` ที่ต้องขอผู้ใช้ยืนยันเพิ่ม: `NoteOptions` (เพดานต่าง ๆ ใน `Jod.Service/Options`), ชื่อตัวตรวจเนื้อหา, ชื่อโมเดลเอกสารเนื้อหา ตำแหน่ง: Entity `Note` อยู่ `Jod.Service/Data` (ไม่ใช่ Domain) และต้องตัดสินว่าจัดโฟลเดอร์ตามฟีเจอร์ (`Note/`) หรือไม่ ตามกฎข้อ 7 และ 10 ของ `backend/CLAUDE.md`
- **ผู้ใช้ปัจจุบัน:** Controller เรียกตัวช่วย `GetUserId()` ของ 1a (ชั้น Web.Jod) แล้วส่ง `userId` เป็นพารามิเตอร์เข้า Service ไม่ส่งรหัสเจ้าของจาก body ของคำขอ

## Testing Decisions

**หลักการ:** ทดสอบพฤติกรรมภายนอก ไม่ทดสอบรายละเอียดภายใน ไม่ทดสอบ private ไม่ทดสอบพฤติกรรมของไลบรารีภายนอก ผลทดสอบมี 4 สถานะ Passed / Failed / Not Tested / Blocked เหมือน ticket 022 ห้ามรายงานว่าผ่านจากการดูหน้าตาอย่างเดียว

**จุดทดสอบ (ผู้ใช้ยืนยัน 2026-10-20) ให้มีน้อยที่สุด**

1. **ฝั่ง backend: HTTP API ของ Note กับ PostgreSQL จริง** ใช้ชุดเทสต์ที่ต่อฐานข้อมูลจริงซึ่ง 1a สร้างไว้ (เรียกผ่าน HTTP ด้วยผู้ใช้ที่ล็อกอินแล้วผ่านตัวตรวจ Google ปลอมในชุดเทสต์ของ 1a) ครอบคลุม: สร้าง/รายการ/อ่าน/บันทึก, ค่าเริ่มต้น, Title ว่าง, เลขเวอร์ชันเพิ่มทีละ 1, 409 พร้อม Note ปัจจุบัน, สองคำขอพร้อมกันด้วยเลขเดียวกันหนึ่งสำเร็จอีกหนึ่ง 409, ผู้ใช้ A เข้า Note ของ B ได้ 404 (ทั้งอ่านและบันทึก), ไม่ล็อกอิน 401, เนื้อหาผิดกติกาแต่ละข้อ 400, เนื้อหาไม่รั่วใน log/error, เนื้อหาเก็บแล้วอ่านกลับได้เท่าเดิมรวมซ้อนลึกและ `id`, ขอบเขตเพดาน (199/200/201), Block ซ้อน 100 ชั้นผ่านและ 101 ชั้น = 400, `baseVersion` ผิดรูป = 400, `OwnerId` ใน body ถูกละเลย
2. **ฝั่งหน้าเว็บ: ตรรกะล้วนด้วย Vitest (ยังไม่เพิ่ม jsdom)** ครอบคลุม: เครื่องจักรสถานะ Autosave (หน่วง 1 วินาที, เพดาน 10 วินาที, ทีละคำขอ, ลองใหม่ 2/5/10 วินาที เฉพาะความผิดพลาดชั่วคราว, ไม่ลองซ้ำ 4xx อื่น, 409, "บันทึกแล้ว" เฉพาะฉบับล่าสุด, แก้ระหว่างบันทึก), การตัดสิน "409 ที่เนื้อหาเท่ากัน = สำเร็จ", การแปลงเอกสาร Block กับ TipTap ไปกลับ, การจัดอันดับคำสั่งในเมนู `/`, การเลือกด้านเปิดของเมนูจากที่ว่าง, Title ว่าง + ส่งซ้ำ = สำเร็จ, หลังส่งทิ้งท้ายต้องดึงก่อนบันทึก, 401 ต่ออายุแล้วลองใหม่ 1 ครั้ง, 408/429 เป็นชั่วคราว, พิมพ์ระหว่างรอ 409, ชนซ้ำถึง 3 ครั้ง, สลับ Note ตอนยังบันทึกไม่เสร็จ, `id` ซ้ำตอนวาง
3. **ตรวจรับด้วยมือบน Editor จริง (เกณฑ์ตรวจรับ ไม่ใช่เทสต์อัตโนมัติ):** รายการ Blocked 7 ข้อของ ticket 022 (Nested Blocks 5 ข้อ, การแตะจริง, แป้นพิมพ์มือถือจริงรวม IME ไทย) และสถานการณ์ Autosave จริงที่ ticket 023 ระบุ (สองแท็บ, ปิดแท็บกลางพิมพ์, สลับแอปบนมือถือ, ตัดเน็ตแล้วต่อใหม่) ผลรายงานเป็น 4 สถานะพร้อมหลักฐาน เพิ่ม: สลับแอปบน iOS Safari (ใช้ `pagehide`), การแสดง Skeleton/Spinner ตามกฎ `client/CLAUDE.md`

**Prior art:** ชุดเทสต์ต่อฐานข้อมูลจริงและตรรกะ auth ล้วนใน `utils/` ที่ 1a สร้าง (รูปแบบที่ควรเดินตาม) เทสต์เดิมของ `Jod.Service.Tests`, `core/http/*.test.ts` และ `modules/auth/utils/refresh-coordinator.test.ts` เป็นตัวอย่างสไตล์ Arrange/Act/Assert
