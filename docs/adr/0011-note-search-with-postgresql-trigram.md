# ค้นหา Note ด้วยข้อความล้วนที่เก็บไว้ + ดัชนี trigram ของ PostgreSQL

ผู้ใช้อนุมัติเมื่อ 2026-11-12 (ticket #43, spec #36 ข้อ Q7)

ค้นชื่อและเนื้อหาของ Note ด้วยการค้นข้อความย่อย (ไม่สนตัวพิมพ์ใหญ่เล็ก) โดยเก็บ "ข้อความล้วน" ของเนื้อหาไว้ในคอลัมน์ `Notes.SearchText` แล้วสร้างดัชนี GIN แบบ trigram (`pg_trgm`, `gin_trgm_ops`) บน `Title` และ `SearchText` ค้นด้วย `ILIKE '%คำ%'` ไม่เพิ่มระบบค้นหาแยก

## Context

- ภาษาไทยไม่มีช่องว่างคั่นคำ ผู้ใช้ต้องการให้ "ไทย" เจอใน "ประเทศไทย" เมื่อค้นแบบข้อความย่อยจึงใช้ได้โดยไม่ต้องตัดคำ และ spec ระบุไม่แก้คำผิด ไม่จัดอันดับตามความเกี่ยวข้อง
- ข้อมูลต่อบัญชีคือราวหนึ่งหมื่น Note กลุ่มผู้ใช้ปิด (ADR 0006) ไม่ต้องการระบบค้นหาแยก (เช่น Elasticsearch) ที่ต้องดูแลและซิงก์เพิ่ม
- เนื้อหา Note เป็น `jsonb` ก้อนเดียว (ADR 0005) ค้นตรง ๆ ใน JSON ทุกครั้งช้าและตัดข้อความไม่ได้ จึงต้องมีข้อความล้วนแยกไว้

## Decision

- เพิ่ม `Notes.SearchText` (text, ไม่ว่าง, ค่าเริ่มต้นว่าง) = ทุกค่าสตริงของ property ชื่อ `text` ที่เจอในเอกสารเนื้อหาทุกระดับความลึก คั่นด้วยขึ้นบรรทัดใหม่ Context ไม่รวมอยู่ในนี้ (ไม่ค้น Context)
- ฝั่งโค้ด `NoteSearchText` สร้างค่านี้ตอนสร้างและตอนบันทึกเนื้อหา ในคำสั่งเขียนเดียวกับ `Content` ส่วน Note เก่าเติมด้วย SQL ใน migration `AddNoteSearch` ผลของทั้งสองทางต้องเท่ากัน (มีเทสต์เทียบด้วยเอกสารหลายแบบ)
- เปิดส่วนขยาย `pg_trgm` และสร้างดัชนี GIN `gin_trgm_ops` บน `Title` และ `SearchText`
- ค้นด้วย `ILIKE` ที่ใช้พารามิเตอร์เสมอ ตัวอักษร `%`, `_` และ `\` ในคำค้นถูก escape ให้เป็นตัวอักษรธรรมดา
- ลำดับ: ชื่อตรงก่อน แล้วเจอเฉพาะในเนื้อหา แต่ละกลุ่มแก้ล่าสุดก่อน เสมอกันเรียงตามรหัส ข้อความตัวอย่างตัดฝั่ง backend ไฮไลต์ทำฝั่งหน้าเว็บ

## Considered Options

- Full-text search ของ PostgreSQL (`tsvector`): ต้องตัดคำ ภาษาไทยไม่มีตัวตัดคำมาตรฐานใน PostgreSQL ค้น "ไทย" ใน "ประเทศไทย" ไม่เจอ และมีการแปลงคำ (stemming) ที่ spec ไม่ต้องการ
- ระบบค้นหาแยก (Elasticsearch, Meilisearch ฯลฯ): ต้องดูแลเพิ่มและซิงก์ข้อมูล เกินความจำเป็นสำหรับหนึ่งหมื่น Note ต่อบัญชี
- `ILIKE` บน `Content::text` โดยไม่มีข้อความล้วน: ค้นเจอ JSON ของโครงสร้าง (ชื่อ property, รหัส Block) ด้วย และไม่มีดัชนีช่วย
- สแกนทั้งตารางโดยไม่มีดัชนี: ใช้ได้ที่ขนาดเล็ก (ดูผลวัดข้างล่าง) แต่โตตามจำนวน Note

## Consequences

- ต้องมีส่วนขยาย `pg_trgm` ในฐานข้อมูล ตั้งแต่ PostgreSQL 13 ส่วนขยายนี้เป็น trusted extension เจ้าของฐานข้อมูลสร้างเองได้โดยไม่ต้องเป็น superuser (ยังไม่ได้ลองกับฐานข้อมูลบริการจริง ตรวจเฉพาะ PostgreSQL 16.15 ใน Docker ที่ผู้ใช้ `jod` ซึ่งเป็น superuser ของ container)
- ฐานข้อมูลต้องใช้ locale แบบ UTF-8 ที่ไม่ใช่ `C` เพราะ pg_trgm นับเฉพาะตัวอักษรและตัวเลขตาม locale ตรวจแล้วว่าฐานข้อมูล `en_US.utf8` ของ Docker สร้าง trigram ของภาษาไทยได้ (`show_trgm('ไทย')` ให้ 4 ค่า) ฐานข้อมูล locale `C` ยังไม่ได้ตรวจ
- ดัชนีใช้ได้กับคำค้นยาว 3 ตัวอักษรขึ้นไป คำค้น 1-2 ตัวอักษรไม่มี trigram พอ PostgreSQL จึงสแกนทั้งตาราง (ผลยังถูก ช้ากว่าตามจำนวน Note ของทั้งระบบ)
- ดัชนีกินที่และทำให้การเขียนช้าลงเล็กน้อย (GIN ของข้อความยาว) ยังไม่ได้วัดขนาดดัชนีและเวลาเขียน
- กติกาที่ต้องรักษา: ทุกที่ที่เขียน `Content` ต้องเขียน `SearchText` ในคำสั่งเดียวกัน ตอนนี้มีสองที่คือสร้าง Note (`NoteService.CreateAsync`) และบันทึก (`NoteService.UpdateAsync`) ฟีเจอร์ใหม่ที่เขียน `Content` (เช่น Merge, Undo ของ AI) ต้องทำเหมือนกัน ถ้าเปลี่ยนวิธีดึงข้อความ ต้องเปลี่ยน `NoteSearchText` และ SQL เติมย้อนหลังให้ตรงกัน และเติมข้อมูลเก่าใหม่ด้วย migration
- ข้อความตัวอย่างดึง `SearchText` ทั้งก้อนของสูงสุด 51 Note ต่อหน้ามาตัดฝั่ง backend ถ้า Note ใหญ่มาก (เนื้อหาได้ถึง 1 MiB) ควรย้ายการตัดไปทำใน SQL
- ตัวพิมพ์ใหญ่เล็กตามกฎของ `ILIKE` ใน PostgreSQL แต่ข้อความตัวอย่างใช้กฎของ .NET (OrdinalIgnoreCase) ตัวอักษรบางตัวนอก ASCII อาจต่างกัน ผลคือข้อความตัวอย่างเป็นต้นข้อความแทนที่จะอยู่รอบคำที่เจอ ไม่ทำให้ผลค้นผิด
- Trash และการกรองตาม Note แม่ ทำใน ticket #44 โดยเพิ่มเงื่อนไขบนคำสั่งค้นเดิม ไม่ต้องเปลี่ยนคอลัมน์หรือดัชนี

## ผลวัดจริง (2026-11-12, PostgreSQL 16.15 ใน Docker, เครื่องพัฒนา)

ข้อมูลสังเคราะห์ ไม่ใช่ข้อความจริงของผู้ใช้: Note เฉลี่ย 600 ตัวอักษร ประกอบจากวลีไทยและอังกฤษราว 57 วลี จึงมีคำที่ซ้ำมากกว่าข้อความจริง คำค้นสั้นและคำไทยทั่วไปเจอเกือบทุก Note ผลที่ได้จึงเป็น "กรณีแย่" ของคำที่เจอเยอะ ไม่ใช่ตัวแทนของคำที่เจอน้อย

**A. ผ่าน HTTP (endpoint จริง, TestServer ในเครื่องเดียวกัน, 5,000 Note ของผู้ใช้เดียว, 7 ครั้งต่อคำค้น, มัธยฐาน เป็น ms)**

| คำค้น | Note ที่เจอ | มีดัชนี | ไม่มีดัชนี |
| --- | --- | --- | --- |
| `ก` (1 ตัว) | 4,985 | 63.6 | 52.0 |
| `นา` (2 ตัว) | 3,899 | 80.1 | 149.1 |
| `ไทย` (3 ตัว) | 4,454 | 82.0 | 85.1 |
| `ประเทศไทย` (9 ตัว) | 2,755 | 69.7 | 63.3 |
| `สหกรณ์ออมทรัพย์` (15 ตัว, เจอน้อย) | 242 | 68.6 | 95.3 |
| `report` | 2,604 | 52.7 | 60.9 |
| `zzzz-none` (ไม่เจอ) | 0 | 55.6 | 72.2 |
| คำค้นว่าง (ไม่แตะฐานข้อมูล) | 0 | 1.1 | 1.6 |

ค่าสูงสุดของแต่ละแถวกระโดดถึง 100-400 ms เป็นครั้งคราว (ไม่ได้แยกสาเหตุ) ตัวเลขนี้มีเวลาของ TestServer, JWT และการอ่าน/แปลงผลรวมอยู่ด้วย

ข้อสังเกตสำคัญ: ในตาราง 5,000 แถวของผู้ใช้เดียว **PostgreSQL เลือกสแกนทั้งตารางทั้งที่มีดัชนี** (ตรวจด้วย `EXPLAIN ANALYZE`) คอลัมน์ "มีดัชนี" จึงเป็นการสแกนทั้งตารางเช่นกัน ตัวเลขสองคอลัมน์ต่างกันเพราะความแกว่งของการวัด ไม่ใช่เพราะดัชนี ตัวคำสั่งค้นเองใช้เวลา 26-114 ms ใน `EXPLAIN ANALYZE` ส่วนที่เหลือคือ overhead ของแอป

**B. ระดับ SQL (`EXPLAIN ANALYZE` ของคำสั่งค้นจริง, 45,000 Note ในตาราง โดย 5,000 เป็นของผู้ใช้ที่ค้น และอีก 40,000 เป็นของผู้ใช้อื่น 4 คน)**

| คำค้น | แผนที่ PostgreSQL เลือก | เวลาคำสั่ง (ms) |
| --- | --- | --- |
| `zzzz-none` (ไม่เจอ) | BitmapOr ของดัชนี trigram ทั้งสอง | 9.7 |
| `ไทย` (เจอ 4,991 จาก 5,000) | BitmapAnd ของดัชนีเจ้าของกับดัชนี trigram | 162.7 |
| `ประเทศไทย` (เจอ 4,315) | BitmapAnd เช่นเดียวกัน | 101.5 |
| `ก` (1 ตัว) | ดัชนีเจ้าของ + กรอง (ไม่มี trigram ให้ใช้) | 55.3 |
| `นา` (2 ตัว) | ดัชนีเจ้าของ + กรอง | 139.1 (84.1 เมื่อปิด seq scan) |

และบนตาราง 5,000 แถวของผู้ใช้เดียว คำค้นที่ไม่เจอ: สแกนทั้งตาราง 41-44 ms เทียบกับ 5.9 ms เมื่อค้นเฉพาะ `Title OR SearchText` ด้วยดัชนี trigram (บังคับให้ใช้ดัชนี)

สรุปที่ตรวจได้: ดัชนีช่วยมากเมื่อคำค้นเจอน้อย (9.7 ms เทียบ 41 ms) และตารางใหญ่ขึ้น แต่เมื่อคำค้นเจอเกือบทุก Note ต้นทุนอยู่ที่การตรวจ `ILIKE` ซ้ำและการเรียงผลของ Note นับพัน ดัชนีไม่ช่วย และคำค้น 1-2 ตัวอักษรใช้ดัชนี trigram ไม่ได้

**ยังไม่ได้ทดสอบ (Not Tested):** ข้อความไทยจริงของผู้ใช้ (ความถี่ของ trigram ต่างจากข้อมูลสังเคราะห์), ตาราง 10,000 Note ต่อบัญชีหลายบัญชีพร้อมกัน, ขนาดของดัชนีบนดิสก์, เวลาเขียนที่เพิ่มขึ้นจากดัชนี GIN, การค้นขณะมีการเขียนพร้อมกัน, ฐานข้อมูลที่ locale เป็น `C`, การสร้างส่วนขยายด้วยผู้ใช้ที่ไม่ใช่ superuser

## แนวทางถ้าช้าเกินไป (ยังไม่ทำ)

- ถ้าคำค้นที่เจอเยอะช้าเกินรับได้: ตัดจำนวนที่นับ (เช่นหยุดนับหลังหลายร้อยรายการ) หรือเรียงเฉพาะส่วนที่จำเป็น
- ถ้าตัดข้อความตัวอย่างฝั่ง backend หนัก: ย้ายไปตัดใน SQL
