# ล็อกอินด้วย Access token และ Refresh token ที่ Jod ออกเอง

จัดการบัญชี (รหัสผ่าน ล็อกบัญชี ยืนยันอีเมล รีเซ็ตรหัสผ่าน) ด้วย ASP.NET Core Identity แต่ Access token และ Refresh token ให้ Jod ออกและจัดการเอง ตัดสินเมื่อ 2026-10-19 เลือกแบบนี้แทนคุกกี้ของ Identity เพื่อไม่ปิดทางให้ Native App ทีหลัง สลับวิธีล็อกอินทีหลังกระทบทั้งหน้าเว็บและหลังบ้าน

- Access token อายุ 15 นาที เก็บใน Memory ของ Web App
- Refresh token อายุ 30 วัน เก็บใน HttpOnly, Secure Cookie กำหนด SameSite และป้องกัน CSRF หมุนใบใหม่ทุกครั้งที่ใช้สำเร็จ ฐานข้อมูลเก็บเป็น Hash เพิกถอนได้ และตรวจจับการนำใบเก่ากลับมาใช้ซ้ำ
- สิทธิ์: Note เป็นของเจ้าของคนเดียว ทุกการอ่านและแก้ไขตรวจ Owner ฝั่ง Server ผู้รับ Share Link เข้าผ่านรหัสลับของลิงก์แบบอ่านอย่างเดียว
- ลิงก์ยืนยันอีเมลอายุ 24 ชั่วโมง ขอส่งใหม่ได้ไม่เกิน 3 ครั้งต่อชั่วโมง ลิงก์รีเซ็ตรหัสผ่านอายุ 1 ชั่วโมง Token ใช้ได้ครั้งเดียว

## Considered Options

- ASP.NET Core Identity แบบคุกกี้ล้วน: ง่ายกว่าและปลอดภัยโดยปริยาย แต่ไม่ได้เลือก

## Consequences

- หน้าเว็บและ API ต้องอยู่ origin เดียวกัน เพื่อให้ SameSite และการป้องกัน CSRF ทำงาน
- เปิดหลายแท็บ: ทุกแท็บต้องขอ Access token ใหม่ด้วย Refresh token ใบเดียวกัน ฝั่ง Client ต้องประสานแท็บให้มีคำขอ Refresh เพียงคำขอเดียวในเวลาเดียวกัน (เช่น Web Locks API) ฝั่ง Server ไม่มีช่วงผ่อนผันให้ใช้ใบเก่าซ้ำ การประสานต้องออกแบบและทดสอบตอนทำ Editor/Client จริง
- ความเสี่ยงที่ยอมรับ: ถ้าคำขอ Refresh สำเร็จที่ Server แต่ตอบกลับไม่ถึง Client แล้วลองใหม่ด้วยใบเดิม จะถูกมองว่าใช้ซ้ำและอาจถูกเพิกถอน ผู้ใช้ต้องล็อกอินใหม่
- ลงมือจริงแล้ว Autosave ต้องไม่ทำเนื้อหาหายเมื่อ Access token หมดอายุระหว่างพิมพ์ (ตาม Spec: บันทึกไม่สำเร็จ = เนื้อหายังอยู่ในจอ ลองใหม่ได้)
- ต้องตรวจว่า Identity ต้องใช้แพ็กเกจใดใน `Jod.Domain` ให้ไม่ขัดกฎ "Domain ไม่ต่อฐานข้อมูล" ก่อนลงมือ
