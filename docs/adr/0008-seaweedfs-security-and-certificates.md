# ตั้งค่าความปลอดภัยของ SeaweedFS: แยกเครือข่าย, JWT, mTLS และใบรับรอง

ทดสอบ PoC (branch `prototype/seaweedfs-s3`) พบว่า SeaweedFS ปล่อยพอร์ต filer/master/volume/gRPC โดยไม่ต้องมีรหัสเป็นค่าเริ่มต้น คอนเทนเนอร์อื่นในเครือข่าย Docker เดียวกันอ่าน เขียน และลบไฟล์ได้โดยข้าม S3 จึงกำหนดข้อบังคับต่อไปนี้เมื่อ 2026-10-19 การเลือก SeaweedFS ดู ADR 0001

## [ตัดสินใจ] ข้อบังคับ

- เครือข่าย Docker เฉพาะที่มีแค่ SeaweedFS กับ Backend และไม่เปิดพอร์ตสู่โฮสต์ในการใช้งานจริง (ชุดทดสอบยังเปิด `127.0.0.1:8333` เฉพาะเพื่อให้โปรแกรมทดสอบรันได้ การปิดพอร์ตทั้งหมดเป็นเงื่อนไขก่อน Production)
- JWT ทั้ง 4 ตัว ตรวจชื่อกับค่าที่ใช้จริงใน PoC แล้ว (`docker-compose.final.yml` ใน branch PoC): `WEED_JWT_SIGNING_KEY`, `WEED_JWT_SIGNING_READ_KEY`, `WEED_JWT_FILER_SIGNING_KEY`, `WEED_JWT_FILER_SIGNING_READ_KEY`
- gRPC mutual TLS ทุกบริการ (volume, master, filer, s3, admin, worker) พร้อมจำกัดชื่อใบรับรอง (`allowed_commonNames = "seaweedfs"`) และซ่อนรายการไดเรกทอรีของ filer (`filer.expose_directory_metadata.enabled = false`)
- ปิดหน้า Admin (`-admin.ui=false`), ปิด telemetry (`-master.telemetry=false`), ปิด WebDAV (`-webdav=false`) และพอร์ต Iceberg/Lance (`-s3.port.iceberg=0`, `-s3.port.lance=0`)
- ตรึง image เป็นเลขเวอร์ชัน, `restart: unless-stopped`, มี healthcheck
- ตัวตน S3 ของแอปมีสิทธิ์ `Read/Write/List` เฉพาะ bucket ของ Jod ตัวตนผู้ดูแลไม่ให้ Backend ถือ ความลับทั้งหมดอยู่นอก git
- Backend ไม่ถือใบรับรอง เพราะใช้แค่ S3 เท่านั้น

## [ตัดสินใจ] ความเสี่ยงที่ยอมรับ

- Backend ที่ถูกบุกรุกเข้าถึงไฟล์ทั้งหมดใน bucket ได้ เพราะสิทธิ์ของที่เก็บแบ่งระดับ bucket ไม่ใช่ระดับผู้ใช้ Jod กฎว่าไฟล์เป็นของ Note ใคร บังคับที่ Backend เท่านั้น
- ผู้ที่ใช้ Docker บนโฮสต์ได้เห็นตัวแปรลับและไฟล์ตั้งค่า (ถือเป็นผู้ดูแลเต็มสิทธิ์)
- พอร์ต `/dir/assign` ของ master ตอบ fid ให้ใครก็ได้ในเครือข่าย แต่เขียนต่อไม่ได้หากไม่มี JWT

## ขั้นตอนเปลี่ยนใบรับรอง (ทดสอบแล้วในการตั้งค่าชุด C ของ ADR 0001)

- เปลี่ยนใบรับรองตัวเซิร์ฟเวอร์ (CA เดิม) แล้ว restart
- เปลี่ยน CA แบบทับซ้อน 3 ขั้น: รวม CA เก่า+ใหม่ → ใช้ใบรับรองใหม่ → ถอด CA เก่า ผ่านทุกขั้น และหลังถอด ไคลเอนต์ที่ถือใบรับรองเก่าถูกปฏิเสธ
- ไม่รีโหลดเองในช่วง 15 วินาทีที่ทดสอบ ต้อง restart (S3 หยุดราว 6 วินาที) ยังไม่ได้ทดสอบการรอนานกว่านี้

## [ข้อเสนอ] นโยบายใบรับรอง

ยังไม่ใช่ Decision ที่ยืนยันแล้ว ตัวเลขอายุยังไม่ได้ทดสอบ (ทดสอบแค่อายุ 30 วันและสั้นกว่า)

- CA ส่วนตัวสร้างครั้งเดียวบนเครื่องผู้ดูแล กุญแจ CA เก็บออฟไลน์ ไม่อยู่บนเครื่องที่รัน Docker
- ใบรับรองของ SeaweedFS (CN `seaweedfs`) อายุ 1 ปี และ CA อายุ 3–5 ปี
- กุญแจและใบรับรองเป็นไฟล์สิทธิ์อ่านอย่างเดียว mount แบบ read-only (Docker secrets ตอนใช้งานจริง)
- ตรวจวันหมดอายุเป็นรอบ และเตือนล่วงหน้า 60 วัน

## [เงื่อนไขก่อน Production]

1. ตัวเตือนความหมดอายุใบรับรอง (ยังไม่ได้สร้างหรือทดสอบ) เพราะทดสอบพบว่าใบรับรองเซิร์ฟเวอร์ที่หมดอายุทำให้ระบบที่รันอยู่ทำงานต่อได้จนกว่าจะ restart จากนั้น S3 ใช้ไม่ได้ทั้งที่คอนเทนเนอร์ยังขึ้นสถานะ "running" และมีเพียง log ว่า handshake ไม่ผ่าน
2. ทดสอบ healthcheck ขณะใบรับรองหมดอายุ
3. ยืนยันนโยบายใบรับรอง (ตัวเลขอายุและขั้นตอน) บน Linux จริงที่จะใช้งาน
4. ปิดพอร์ตสู่โฮสต์ทั้งหมดและทดสอบซ้ำภายใต้การตั้งค่านั้น
5. ขั้นตอนสำรอง/กู้คืนต้องรวมไฟล์ตั้งค่า ใบรับรอง และคีย์ ซึ่งไม่อยู่ใน volume
6. งานเก็บกวาด multipart ที่ค้าง (เกิดเมื่อ storage ดับกลางอัปโหลด ทดสอบแล้วว่ายกเลิกรายการค้างได้) และเผื่อพื้นที่ดิสก์ (พื้นที่คืนช้าราว 15–16 นาทีหลังลบ ตัวเลขจากการทดสอบที่มีงานอื่นรันปนอยู่)

## [ยังไม่ได้ทดสอบ]

- บริการ IAM ของ filer ผ่าน gRPC เรียกตรงๆ (มีแค่ log ว่าต้องใช้โทเคน admin เมื่อตั้ง JWT และผลว่าพอร์ตถูกปิดด้วย mTLS)
- healthcheck ขณะใบรับรองหมดอายุ
- Linux จริง (ทดสอบบน Docker Desktop บน Windows)
- การรีโหลดใบรับรองเมื่อรอนานกว่า 15 วินาที
- ผลต่อความเร็วของ mTLS
- การเข้าถึง unix socket จากคอนเทนเนอร์ที่ใช้ volume ร่วม
