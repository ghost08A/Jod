# ล็อกอินด้วย Google Sign-In เท่านั้น และ Jod ออก Access token กับ Refresh token เอง

ตัดสินเมื่อ 2026-10-20 (ผู้ใช้ยืนยัน) Jod ใช้ Google Sign-In เป็นวิธียืนยันตัวตนวิธีเดียว Jod ไม่เก็บรหัสผ่านและไม่ส่งอีเมลเพื่อยืนยันตัวตนใดๆ (ไม่มีสมัครด้วยรหัสผ่าน ลืมรหัสผ่าน หรือลิงก์ยืนยันอีเมล) เมื่อ Backend ตรวจ Google ID token ผ่านแล้ว Jod ออก Access token และ Refresh token ของตัวเอง โครงของ token ที่ตัดสินไว้เมื่อ 2026-10-19 ยังใช้ต่อทั้งหมด ADR นี้แทน ADR 0006 ฉบับเดิม (ล็อกอินด้วยรหัสผ่านผ่าน ASP.NET Core Identity) และแทน ADR 0007 (ส่งอีเมลผ่าน Mailpit) ซึ่งถูกลบแล้ว

## ตัวตน (ผู้ใช้ยืนยันแล้ว)

- ผู้ใช้กดปุ่ม "Sign in with Google" ในหน้าเว็บ ได้ ID token (JWT ที่ Google เซ็น) หน้าเว็บส่งให้ Backend ที่ `POST /api/auth/google` Backend ไม่เชื่อชื่อ อีเมล หรือรหัสผู้ใช้ที่หน้าเว็บส่งมาเอง ใช้เฉพาะค่าในโทเคนที่ตรวจผ่านแล้ว
- Backend ตรวจ ID token ทุกครั้ง: ลายเซ็นด้วยกุญแจสาธารณะของ Google (กุญแจหมุนเวียน ต้องแคชตามอายุที่ Google ระบุ ห้ามฝังกุญแจไว้ในโค้ด), `aud` ตรงกับ Client ID ของ Jod, `iss` เป็น `accounts.google.com` หรือ `https://accounts.google.com`, `exp` ยังไม่หมดอายุ และ `email_verified` เป็นจริง (ตรวจจากเอกสาร Google เมื่อ 2026-10-20: <https://developers.google.com/identity/gsi/web/guides/verify-google-id-token>)
- ตัวระบุตัวตนคือ Google `sub` (ไม่ซ้ำ ไม่ถูกนำกลับมาใช้) เก็บผูกกับผู้ใช้ใน Jod อีเมลไม่ใช่กุญแจ เป็นข้อมูลที่อัปเดตตามโทเคนล่าสุดเท่านั้น เพราะบัญชี Google เปลี่ยนอีเมลได้
- Client ID ไม่ใช่ความลับ ใส่ในไฟล์ตั้งค่าได้ ไม่ใช้ Client Secret เพราะรับ ID token จากหน้าเว็บโดยตรง ไม่ใช้ authorization code flow

## กลุ่มปิด [ร่าง รอผู้ใช้อนุมัติแผนเปลี่ยนโค้ด]

- Jod เป็นกลุ่มปิด การล็อกอินด้วย Google สำเร็จไม่ได้แปลว่าใช้ Jod ได้ ต้องอยู่ใน "รายชื่ออีเมลที่อนุญาต" ด้วย
- ค่าเริ่มต้นคือไม่อนุญาตใคร รายชื่อว่าง = ไม่มีใครเข้าได้ ไม่มีโหมด "เปิดสมัครสาธารณะ" ในสภาพแวดล้อมใดเลย (กันการเปิดสาธารณะโดยไม่ตั้งใจ)
- ตรวจตอนล็อกอิน (ทั้งผู้ใช้ใหม่และเดิม) และตอนต่ออายุ session: ถ้าอีเมลถูกเอาออกจากรายชื่อ Refresh token ถูกปฏิเสธและเพิกถอนทั้งชุด ผู้ใช้เสียสิทธิ์ภายใน 15 นาที (อายุของ Access token)
- รายชื่อเก็บในค่าตั้งค่าของ Backend (รายการอีเมล เทียบโดยไม่สนตัวพิมพ์เล็กใหญ่) แก้ได้โดยผู้ดูแลที่เข้าถึงเซิร์ฟเวอร์ ไม่มีหน้าจัดการใน v1 (OQ-12)
- ยอมรับ token เมื่อ `email_verified` เป็นจริง **และ** (มี `hd` หรืออีเมลลงท้าย `@gmail.com`) เพราะเอกสาร Google ระบุว่า Google เป็นผู้ยืนยันอีเมลที่เชื่อถือได้เฉพาะ Gmail และบัญชี Workspace ส่วนอีเมลอื่นแนะนำให้ยืนยันเพิ่ม ผลคือเพื่อนที่ใช้บัญชี Google กับอีเมลผู้ให้บริการอื่นล็อกอินไม่ได้จนกว่าจะตัดสิน (OQ-11)
- `POST /api/auth/google` ต้องมีหัวข้อ `X-Requested-With: jod` เหมือน refresh/logout และอยู่ใต้โควตา `auth` ต่อ IP

## โครง token (ตัดสินแล้ว 2026-10-19 ยังมีผล)

- Access token อายุ 15 นาที เก็บใน Memory ของ Web App เป็น JWT ที่ Jod ออกเอง (`sub` = รหัสผู้ใช้ใน Jod ไม่ใช่ Google `sub`)
- Refresh token อายุ 30 วัน เก็บใน HttpOnly, Secure Cookie กำหนด SameSite และป้องกัน CSRF หมุนใบใหม่ทุกครั้งที่ใช้สำเร็จ ฐานข้อมูลเก็บเป็น Hash เพิกถอนได้ และตรวจจับการนำใบเก่ากลับมาใช้ซ้ำ (ใช้ซ้ำ = เพิกถอนทั้งชุด) ไม่มีช่วงผ่อนผันฝั่ง Server
- สิทธิ์: Note เป็นของเจ้าของคนเดียว ทุกการอ่านและแก้ไขตรวจ Owner ฝั่ง Server ผู้รับ Share Link เข้าผ่านรหัสลับของลิงก์แบบอ่านอย่างเดียว

## Considered Options

- Google + Email/รหัสผ่านที่ Jod จัดการเอง: ไม่เลือก ต้องดูแลสองเส้นทาง ต้องเก็บรหัสผ่าน ล็อกบัญชี ลิงก์ยืนยัน/รีเซ็ต และส่งอีเมล (ซึ่งไม่มีงบ)
- Google แบบ authorization code + คุกกี้ external login ของเฟรมเวิร์ก (`AddGoogle`): ไม่เลือก ต้องใช้ Client Secret และผูกกับคุกกี้ของเฟรมเวิร์ก ขัดกับ token ที่ Jod ออกเอง
- ASP.NET Core Identity แบบคุกกี้ล้วน: ไม่เลือก (ตัดสินไว้ตั้งแต่ฉบับเดิม)

## Consequences

- ตัดออก: รหัสผ่านและการเก็บแฮช, ล็อกบัญชีเมื่อรหัสผิด, ลิงก์ยืนยัน/รีเซ็ต, `IEmailService`/SMTP/Mailpit, โหมดสมัครเปิด/ปิด, งานช่วง 1c ทั้งก้อน
- ทุกบัญชีมีอีเมลที่ Google ยืนยันแล้วเสมอ จึงไม่มีสถานะ "ยังไม่ยืนยัน"
- เพื่อนทุกคนต้องมีบัญชี Google และผู้ดูแลต้องใส่อีเมลของเขาในรายชื่อก่อน
- ถ้าบัญชี Google ของใครถูกปิดหรือเปลี่ยน จะได้ `sub` ใหม่ = ผู้ใช้ใหม่ เข้าพื้นที่ Note เดิมไม่ได้เอง ผู้ดูแลต้องแก้ข้อมูลให้ (OQ-14)
- ล็อกอินครั้งใหม่ขึ้นกับ Google ถ้า Google ล่ม ล็อกอินใหม่ไม่ได้ แต่ session ที่มีอยู่ใช้ต่อได้ถึง 30 วัน
- ต้องมี OAuth Client ID ชนิด Web ใน Google Cloud กำหนด Authorized JavaScript origins ให้ตรงกับที่ใช้จริง (OQ-13)
- หน้าเว็บและ API ต้องอยู่ origin เดียวกัน เพื่อให้ SameSite และการป้องกัน CSRF ทำงาน
- เปิดหลายแท็บ: ทุกแท็บต้องขอ Access token ใหม่ด้วย Refresh token ใบเดียวกัน ฝั่ง Client ต้องประสานแท็บให้มีคำขอ Refresh เพียงคำขอเดียวในเวลาเดียวกัน (เช่น Web Locks API) ฝั่ง Server ไม่มีช่วงผ่อนผัน
- ความเสี่ยงที่ยอมรับ: ถ้าคำขอ Refresh สำเร็จที่ Server แต่ตอบกลับไม่ถึง Client แล้วลองใหม่ด้วยใบเดิม จะถูกมองว่าใช้ซ้ำและอาจถูกเพิกถอน ผู้ใช้ต้องล็อกอินใหม่
- ลงมือจริงแล้ว Autosave ต้องไม่ทำเนื้อหาหายเมื่อ Access token หมดอายุระหว่างพิมพ์ (ตาม Spec: บันทึกไม่สำเร็จ = เนื้อหายังอยู่ในจอ ลองใหม่ได้)

## [ยังไม่ได้ตรวจ] (ต้องตรวจก่อนลงมือ)

- nonce / การกันนำ ID token เก่ากลับมาใช้ซ้ำ ในโหมด JavaScript callback: หน้าเอกสาร Google ที่ตรวจไม่ระบุ ต้องอ่านเอกสาร Google Identity Services ก่อน
- ไลบรารี `Google.Apis.Auth` 1.77.0 (Apache-2.0, รองรับ net6.0/netstandard2.0 ตามข้อมูล NuGet) ใช้กับ .NET 10 ได้หรือไม่ (ยังไม่ได้ทดลองรัน) ทางเลือกคือใช้ไลบรารี JWT ที่มีอยู่ตรวจเอง
- พฤติกรรมปุ่ม Google บนมือถือและกรณีที่ผู้ใช้ปิดคุกกี้ของบุคคลที่สาม
- ข้อจำกัดของหน้าจอขอความยินยอม (consent screen) ตอนเป็นโหมดทดสอบ และผู้ที่ต้องเป็นเจ้าของ Client ID (OQ-13)
- กฎ "`hd` หรือ `@gmail.com`" เหมาะกับกลุ่มเพื่อนจริงหรือไม่ (OQ-11)
