# ลิงก์แชร์: คำนวณสิทธิ์ตอนมีคำขอ และให้ผู้รับใช้ endpoint ดูอย่างเดียวแยก

ตัดสินเมื่อ 2026-10-19 เซตของ Note ที่ Share Link เปิดได้ (ลูกหลานทั้งกิ่ง และตามการ์ดต่อเนื่อง ตาม ticket 009) คำนวณตอนมีคำขอ ไม่เก็บรายการไว้ล่วงหน้าต่อลิงก์ เพราะย้าย ลบ กู้ Merge และแก้การ์ดทำให้เซตเปลี่ยนตลอด และกฎกำหนดให้ของใหม่ถูกแชร์อัตโนมัติและลิงก์ใช้ไม่ได้ทันที ผู้รับใช้ endpoint แยกสำหรับดูอย่างเดียว พร้อมชนิดข้อมูลตอบกลับของตัวเอง endpoint ของเจ้าของไม่ยอมรับโทเคนลิงก์

## [ตัดสินใจ] ข้อกำหนด

1. **ตรวจรากทุกคำขอ:** ลิงก์ใช้ได้เมื่อ ไม่ถูกเพิกถอน, ไม่หมดอายุ, Note รากไม่อยู่ใน Trash และไม่ถูก Merge (ตามกฎใน ticket 009) ไม่แคชใน v1 เพื่อให้การเพิกถอนมีผลทันที
2. **ตรวจ "อยู่ใต้ราก" ก่อน** (ไล่ขึ้นหาแม่ ~0.15 มิลลิวินาที) ถ้าไม่ใช่จึงคำนวณเซตรวมการ์ดด้วย recursive query ที่ใช้ตารางการ์ดทิศไปข้างหน้า (ADR 0005)
3. **ป้องกันวงจร:** การ์ดวนกลับไปยัง Note ที่เคยเข้าถึงแล้วได้ query ต้องใช้ `UNION` (ไม่ใช่ `UNION ALL`) และแถวในส่วน recursive มีเฉพาะรหัส Note เท่านั้น (ห้ามเพิ่มคอลัมน์ความลึกหรือเส้นทาง เพราะจะทำให้การตัดแถวซ้ำไม่ทำงาน) ผลคือ Note หนึ่งถูกประมวลผลครั้งเดียวและ query จบเสมอ
4. **ตรวจสิทธิ์ทุกคำขอที่เข้าถึงข้อมูลผ่านลิงก์ รวมรูปภาพและไฟล์แนบ:** ไฟล์เปิดได้เฉพาะเมื่อมี Note ในเซตที่เปิดได้อ้างถึงไฟล์นั้น (ตามตารางไฟล์อ้างอิงของ ADR 0005) ไฟล์ที่ถูกอ้างโดย Note ใน Trash หรือฉบับ Undo เท่านั้นไม่เปิดผ่านลิงก์
5. **ไม่เปิดเผยข้อมูลต้องห้าม ทั้งทางตรงและทางอ้อม:** ชนิดข้อมูลของผู้รับไม่มีช่อง Context, ข้อเสนอ AI, สถานะ Trash (ทางตรง) และคำตอบสำหรับ Note ที่ไม่มีอยู่ อยู่นอกเซต หรืออยู่ใน Trash ต้องเหมือนกันทั้งรหัสตอบกลับ ข้อความ และรูปแบบ (ทางอ้อม ไม่ให้เดาได้จากความต่างของคำตอบ)

## เงื่อนไขก่อนลงมือทำหน้าดูผ่านลิงก์ (กฎเดิมยังไม่ชัด ห้ามเดา)

- Note ลูกที่ไม่ใช่รากและอยู่ใน Trash ผู้รับเปิดได้หรือไม่ (OQ-8) ต้องตัดสินก่อน การคำนวณต้องกรองสถานะได้ด้วยเงื่อนไขเดียว เพื่อรองรับคำตอบได้ทั้งสองแบบ
- การ์ดที่ชี้ไป Note ที่ถูก Merge ไปแล้ว ผู้รับตาม Alias ได้หรือไม่ (OQ-9) จนกว่าจะตัดสิน ห้ามตาม Alias ในการคำนวณเซต
- ผู้รับดาวน์โหลดไฟล์แนบทั่วไปได้หรือไม่ (OQ-7) จนกว่าจะตัดสิน endpoint ของผู้รับให้บริการเฉพาะรูปภาพ

## ทางเลือกที่ไม่เลือก

- เก็บรายการ Note ที่เปิดได้ล่วงหน้าต่อลิงก์: เร็วตอนอ่าน แต่ต้องอัปเดตทุกลิงก์ทุกครั้งที่ย้าย แก้การ์ด ลบ หรือกู้ และขัดกับกฎแชร์อัตโนมัติ
- ไม่ตามการ์ด: ขัดกับกฎที่ตัดสินไว้ใน ticket 009

## ผลทดสอบ (ข้อมูลสมมติ PostgreSQL 16, 10,000 Note, ต้นไม้สุ่มลึกราว 9 ชั้น)

คำนวณเซตรวมการ์ดใช้ ~2–100 มิลลิวินาที (เลวร้ายสุด: การ์ดสุ่ม 20,000 เส้น ซึ่งมีวงจรอยู่แล้ว ~54–100 มิลลิวินาที และ query จบ ไม่วน) ตรวจ "อยู่ใต้ราก" ~0.15 มิลลิวินาที ผลทดสอบนี้ใช้ `UNION` ตามข้อกำหนดข้อ 3

## [ยังไม่ได้ทดสอบ]

การตาม Alias ของ Note ที่ถูก Merge, การกรอง Note ใน Trash ร่วมกัน, ข้อมูลจริง, คำขอพร้อมกัน (หนึ่งหน้ามีหลายคำขอสำหรับรูป/ไฟล์ ต้องตรวจสิทธิ์ซ้ำ ถ้าช้าเกินไป ค่อยพิจารณาแคชสั้นๆ ซึ่งต้องไม่ทำให้การเพิกถอนล่าช้า), การรั่วทางอ้อมจริง (ความต่างของเวลาตอบกลับ), วงจรสั้นๆ เช่น การ์ดชี้ตัวเองโดยเฉพาะ
